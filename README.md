# Hire Car System

Next.js dashboard for hire-car operations across the Tokyo, Osaka, and Hokkaido regions. Business records are stored in Supabase PostgreSQL. Supabase Auth handles email/password sign-in, and database row-level security isolates ordinary users by region while administrators can access all regions.

## Supabase setup

1. Create a Supabase project and add the project URL, publishable key, service-role key, and a unique `DELETE_CONFIRMATION_PASSWORD` to `.env.local`, using [.env.example](./.env.example) as the template. Set the same variables in the Vercel project. Both the service-role key and delete confirmation password are server-only and must never use a `NEXT_PUBLIC_` prefix.
2. Apply the SQL files in [`supabase/migrations`](./supabase/migrations) in filename order using the Supabase SQL Editor, once each. Never rerun migrations already applied. The initial schema creates starter records; the finance migrations add daily order accounting, vehicle monthly expenses, and balance expenses. The region migrations create Tokyo, Osaka, and Hokkaido and enable region-scoped RLS, including financial records. Vehicle monthly records inherit their vehicle's region; pre-existing balance expense items are assigned to Tokyo. The final finance-region migration must be applied before using the merged application.
3. In Supabase Auth URL Configuration, set the Site URL to the app's origin and add redirect URLs for local development and the deployed app, including `/auth/confirm` for password recovery. Disable public sign-ups; administrators create accounts directly.
4. Create the first administrator from Supabase Dashboard → Authentication → Users. Use **Add user** with an email and password (and confirm the email). The database trigger creates the corresponding profile.
5. Promote that profile in the SQL Editor, replacing the address with the first administrator's email:

   ```sql
   update public.profiles
   set role = 'admin'
   where email = lower('admin@example.com');
   ```

6. Run `npm run dev` and sign in at `/login`. Administrators create accounts with an initial password, assign a region, and choose either role from **登录管理**. No invitation email is sent for either role. Administrators can switch the active view among one region or all regions.

The migration seeds the prototype's sample vehicles, drivers, companies, sources, and two sample orders. Remove those rows before using the project with real operational data if they are not wanted.

Ordinary accounts are assigned to one region and can only read or change that region's business records. Administrators can view and manage records across all regions; new records require a specific active region. The migration assigns pre-existing records and profiles to Tokyo. Deletions require the server-configured `DELETE_CONFIRMATION_PASSWORD`; only administrators can list, invite, edit, promote, or delete accounts.

Account-creation failures distinguish existing accounts, request rate limits and database failures. For `Database error saving new user`, inspect Supabase Auth and Postgres logs for the underlying SQL error and check the `handle_auth_user` trigger, its permissions and applied migrations before retrying. Existing users should be edited rather than recreated. Never share service-role keys, passwords or complete email authentication links when reporting an error.

Apply `20261029000000_account_profile_service_permissions.sql` if the account-management API reports `42501 permission denied for table profiles`. It explicitly grants the server-only `service_role` schema usage and profile read/update permissions required by account administration; it does not grant profile writes to ordinary authenticated users, disable RLS, or change existing accounts. A separate `23505` duplicate-key error requires the full constraint name and database error context to diagnose; this permission migration does not resolve duplicate records.

### Administrator-created accounts and passwords

Accounting-assignee selectors display full names only, without email addresses. Wage details and their print output resolve the stored account email to the same name. Missing names display `未填写姓名`; unavailable historical email accounts display `历史账号（姓名不可用）`. Existing name-only historical values remain visible. This is presentation-only: stored assignee identifiers are not rewritten.

In **登录管理 → 新增账号**, choose the role, enter and confirm an 8–128 character password, and select **创建账号**. Both roles use server-only Supabase Admin `createUser` with email confirmation enabled: this does not send mail or prove mailbox ownership. Verify the recipient and deliver the password through a secure channel. Authentication-service password strength requirements still apply.

For an existing ordinary user, select **编辑**, enter and confirm a new password, and select the separate **设置新密码** button. After confirmation, this also activates a pending email account; **保存资料** alone never changes a password. Password changes do not save other unsaved profile edits and do not promise to immediately revoke existing sessions. The server verifies administrator access and rejects password changes for target administrator accounts. Passwords are not returned by the API, stored in profiles or browser storage, or intentionally logged; fields are cleared after success, cancellation, switching accounts or changing roles. Existing administrators retain their password-recovery flow. The legacy email callback remains for recovery and previously issued links, but account management no longer sends invitations. Duplicate emails must be edited, not recreated. If authentication succeeds but profile setup fails, the API explicitly reports the partial result; inspect permissions and the account list rather than recreating the account.

## Financial reports

The dashboard includes order accounting (`経理統計`), driver wages (`給料統計`), vehicle finances (`車両統計`), and the monthly balance (`收支平衡`). Clicking an order name in the order accounting report opens that order's existing financial statistics editor, including daily entries, accounting status, deposits, and notes. Saving updates the same order and refreshes its calculated report totals.

Below the accounting status, the financial editor records the invoice status (`未完成` or `已完成`, initially `未完成`) and an optional invoice sent date. These are independent of accounting and deposit status; saving and reopening an order preserves both values. Apply `20261021000000_order_invoice_status.sql` before using these fields. Recording a sent date does not send an invoice.

The order accounting table displays invoice status, deposit status, and then request amount immediately after the vehicle number: pending invoices are red and completed invoices are green. The A4 export uses the same column order, with blank status cells on the totals row.

The column after the driver is `車両番号` in both the order accounting table and A4 export. It shows the plate of the matching vehicle in the order's region, or `-` if the vehicle or its plate is unavailable.

The order accounting table and A4 export omit the order status column; source follows the order name, then the driver. This does not change the order's saved status or its display elsewhere.

In `経理統計`, `导出财务表（A4）` replaces CSV export. It prints a portrait A4 monthly report for the current region, source, company, and deposit-status filters, using the same row order and financial calculations as the list. It includes request amounts, advances, expenses, wages, profits, totals, profit rate, and signatures. This internal report is distinct from the expense-only order sheet. The output scales to a single page (long reports have smaller text); select A4 and disable browser headers/footers, or save as PDF.

The login screen uses a navy brand panel and white sign-in form, side-by-side on desktop and stacked on phones. Inputs retain 16px text and at least 48px touch height, with visible focus and error states. This presentation change does not alter authentication, invitation requirements or password recovery.

## Japanese invoice export

Apply `20261022000000_company_invoice_details.sql` before registering company invoice details. Company create/edit forms and the company list include `振込口座` (bank/branch, account type/number, holder) and `T番号` (blank or `T` plus 13 digits). Existing companies receive blank values; edit them before issuing an invoice. T-number format validation does not verify registration with the tax authority. Bulk company import keeps its existing format and initializes these new fields blank.

The order accounting dialog has a `請求書导出（A4）` button. It creates a portrait Japanese invoice using the order source as recipient (including its contact and address) and the order's company as issuer. Issuer address is the company's `营业所地址`, with telephone, registered T number and bank account. This address label replaces the former roll-call label without changing the existing `rollCallAddress` / `roll_call_address` storage fields or data. Associations match both name and region. Missing source/company or incomplete issuer details prevent export with an explicit message.

Invoice contents are the whole-order price plus all current daily ETC trip-report, driver-advance trip-report and company-advance trip-report amounts. The order-name/price line always appears, including a zero order price; each trip-report line appears only when its amount is greater than zero. With no trip-report charges, only the order-name/price line is printed in the item table. All included items are tax-inclusive at 10%. The total is not increased by tax: included tax is calculated once on the total as `total * 10 / 110`, truncated to whole yen. Overtime is not an invoice line in this requested format, so this invoice can differ from the dashboard's request amount, which includes overtime. No wages, profit, or company-report expenses are printed.

The invoice uses the current unsaved editor values, today's local issue date and the order's service period. Its printed item labels omit the internal trip-report suffix; their underlying data remains the trip-report amounts. Printing neither saves financial edits nor changes invoice status/sent date, sends email, or archives an immutable issued invoice. Save the resulting PDF for your records. The layout follows the [National Tax Agency invoice guidance](https://www.nta.go.jp/taxes/shiraberu/zeimokubetsu/shohi/keigenzeiritsu/invoice_tebiki.htm); confirm actual tax treatment and registered issuer details before issuing.

Apply `20261023000000_invoice_serial_numbers.sql` for persistent numbering. Each company record has its own `INV-000001`, `INV-000002`, ... sequence (no monthly reset). An authenticated API calls a database function that locks the order and atomically increments the company counter. Reprinting the same order/company reuses its number, including after cancelling printing. Company names may share the same printed sequence numbers because numbering is independent per company. If an order changes company, it receives a number from the new company's sequence; returning to the original company reuses its prior allocation. Order deletion removes its allocation but does not decrement the company counter. Company deletion removes that company's numbering records. The allocation tables are not directly writable by clients; the function checks order access and current same-region company association. Export requires a live server connection and stops on allocation errors rather than inventing a local number.

Dashboard dialogs close when their backdrop is clicked, without saving pending edits. Clicks inside a dialog do not dismiss it. The delete confirmation cannot be dismissed while deletion is in progress; otherwise dismissal clears its password and error.

For multi-day orders, each daily accounting summary shows only combined ETC, fuel cost, fuel consumption, and calculated fuel unit price (cost divided by liters, up to two decimal places in JPY/L). Zero consumption displays a dash instead of a unit price. Single-day orders retain daily request/profit summaries; whole-order financial totals and saved calculations are unchanged.

The accounting dialog's `一键导出／打印（A4）` button opens the browser print dialog for a portrait A4 expense sheet (also supports Save as PDF). It uses the current editor values without saving them. The isolated print document includes daily drivers/plates, ETC, fuel, both types of advances, overtime, wages, totals, notes, and signature lines. It does not include order price, request amount, profit, invoice status, or deposit details. Percentage-based wages use the existing calculation. Overtime is shown as a component of wages, not an additional cost. The sheet scales down to fit one page; long trips or long notes will produce smaller text. Use A4 with browser headers/footers disabled. Free-text names and notes are printed verbatim, so remove any confidential details from them before exporting.

The A4 sheet groups all information by date in ascending order. Each daily block starts with the date, driver, and vehicle number, followed by that day's ETC, fuel, advances, overtime, and wages together. Whole-order expense totals appear after the daily blocks.

In `車両統計`, `导出车辆财务表（A4）` replaces CSV export. All-vehicle mode shows one row per vehicle in both the dashboard and portrait A4 export: service month, plate, total request, driver advances, company payments, driver wages, fixed costs/supplies, and net order profit. Net order profit equals request minus advances, company payments, wages and fixed costs/supplies (parking, insurance, inspection, repairs and supplies). The footer totals every monetary column and highlights aggregate profit. Monthly fixed costs are deducted once per vehicle, using the selected month's saved record, or default parking/insurance when no record exists; saved zero amounts remain zero. All registered vehicles in the active region scope are included, even without operating records. Historical unmatched vehicle names remain as labeled rows with unknown fixed costs provisionally counted as zero; same-region duplicate names with operating records block aggregation with an explicit error rather than assigning revenue arbitrarily. Cross-region names are kept separate.

Selecting one vehicle retains daily orders and the existing monthly fee/supplies/odometer editor. Its A4 report includes current unsaved monthly inputs, distance, net profit and profit per kilometer; exporting does not save inputs. All-vehicle summaries use only saved monthly fees/defaults, not unsaved edits. Invalid expenses or reversed odometers block single-vehicle printing; missing/zero distance displays a dash for per-kilometer profit. Ambiguous same-name single-vehicle selection requires choosing a specific region first. Reports include signatures and scale to one A4 page; long lists produce smaller text. Use A4 with browser headers/footers disabled or Save as PDF.

Vehicle financial reports identify vehicles by `車両番号` (plate), without appending vehicle names. Missing plates are explicitly labeled rather than falling back to vehicle names; unmatched historical records retain their financial amounts with an unknown-number label.

All-vehicle summaries include outsourced vehicles as well as owned vehicles, including registered outsourced vehicles without operating records. An `外注` marker accompanies their plate (or missing-number notice) in both the dashboard and A4 export. Unregistered historical outsourced entries remain separately grouped by region/name internally, are marked as outsourced, and contribute to totals.

In reservation management, clicking a driver's name (or the unassigned label) opens a driver-selection dialog with name buttons instead of a dropdown. The new/edit reservation form uses the same dialog. Candidates are restricted to the order's region and sorted from top left by distinct service days in the last 30 calendar days including today, then by name. This is based on reservation service dates, using daily financial driver overrides when available and otherwise the reservation driver; cancelled orders, rest days and future dates are excluded. It is not an attendance ledger. The dialog supports search, manual names, clearing assignment, Escape, outside-click cancellation and keyboard focus containment. List selection saves the reservation driver through existing persistence without changing financial entries; form selection remains unsaved until the reservation is saved.

`経理統計` includes an invoice-status filter immediately before deposit status: all, pending (`未完成`), or completed (`已完成`). It combines with the existing month/region/source/company/deposit filters, updates totals, and is included in the A4 report's filter description. Changing regions resets both status filters to all.

Company records support optional seal upload, preview, replacement and removal. PNG/JPEG/WebP originals up to 2MB are decoded and re-encoded to PNG with a maximum side of 512 pixels; encoded data is limited to 350,000 characters. Transparent PNG is recommended. The small image is stored directly in the company's `seal_image` field under existing company region/RLS access, not a public storage URL. Invoices use the selected order's same-region issuing company seal beside its name; no seal is required and existing invoice amounts/serials remain unchanged. Printing waits for image decoding and reports load failures instead of printing silently without the seal.

The reservation calendar's `全体车辆` tab includes registered owned and outsourced vehicles within the active region scope. Model-specific tabs still show owned vehicles of that model, and `外注` still shows outsourced vehicles only.

The calendar grid scrolls vertically and horizontally inside a container capped at 75% of the viewport height. Its date header stays pinned at the top while scrolling vehicle rows, and shares horizontal scrolling with the grid to keep dates aligned. Ordinary mouse-wheel input scrolls vertically rather than being converted to horizontal movement; horizontal trackpad/scrollbar input remains available.

On phones below 640px, the dashboard uses two-column header actions, horizontally scrollable navigation and wrapping report filters. Form controls use 16px text to avoid focus zoom on mobile browsers, with 44px minimum touch targets for major actions and table buttons. Wide business tables and the calendar retain their own horizontal scrolling rather than shrinking financial text or hiding columns. Dialogs use reduced padding and dynamic-viewport height limits with internal scrolling; the calendar date slider respects the bottom safe area. The login form uses dynamic viewport height, full-width controls and the same touch sizing. Desktop layouts, business permissions, calculations and A4 print templates are unchanged.

Vehicle lists and selectors share the model order Alphard (阿尔法), Hiace (海狮), Tesla (特斯拉), then outsourced (外注) vehicles. Unclassified owned vehicles appear after Tesla and before outsourced vehicles. Within each group, names use natural numeric ordering (for example 2 before 10). The vehicle management list, calendar, reservation/accounting selectors, and all-vehicle financial dashboard/A4 report use this order, without exposing vehicle names in plate-only reports or changing regional filtering.

`收支平衡` exports a portrait A4 report instead of CSV. Income and expense projects have separate tables and save buttons, with persistent company-specific names and separately entered amounts each month. Only in balance reports, the entire order request is assigned to the month of the first actual service date (inclusive start/end, excluding rest dates), without daily or cross-month allocation. It includes the base order price once plus all dated ETC trip-report, driver advance trip-report, company advance trip-report and overtime amounts, including entries in later months. Orders without saved daily records still contribute their base price. An order with no eligible service date produces an explicit error. Requests belong to the order company. Other order accounting, wage, vehicle and invoice calculations remain unchanged.

The A4 report follows the selected month, region and company, with request/other-income/expense/net summaries, separate manual income and expense details, totals, a final monthly result and signature lines. It uses current manual income/expense edits (blank means zero) without saving them; invalid amounts or unavailable data explicitly block both the financial summary and export instead of showing a false zero. There are no automatic deductions for wages, vehicle fees, advances or operating payments. Vehicle monthly records are not required or read by balance calculations. Both dashboard and print show black `当月利润` for positive/zero net results and red `当月亏损` for negative results, retaining the signed amount. Print scaling fits the report onto one A4 page; large lists use smaller text.

The bottom summary cards show driver advances and company advances separately, each totaling its own company-report and trip-report amounts.

### Business operation history

Apply `20261028000000_audit_actor_names.sql` to display the user's full name only, with `未填写姓名` for accounts without a name; email is no longer an operator-name fallback. The migration replaces existing email-based operator labels using the linked profile name (or the unnamed label if the account is unavailable), without changing business data, actor IDs or operation timestamps. Non-email historical names remain unchanged. The last-operation metadata correction temporarily disables only the two audit triggers on each affected table inside the same transaction and restores them before commit; it does not generate artificial business edits.

Apply `supabase/migrations/20261026000000_business_audit.sql` before deploying the audit feature. Database triggers record inserts, real updates and deletions for orders (including daily finance, invoice/deposit status), drivers, vehicles, sources, companies, vehicle monthly expenses, balance expense items and invoice-number allocations. Each event and its business write share the same database transaction: a log-write failure rejects the business write. Upserts do not produce duplicate insertion events; identical saves do not change the last operator or create a log.

Only the reservation editor and reservation details show the last confirmed operator's name and Japan-local time, updated from the server after saving. The reservation management list, other business screens and finance dialogs do not display this inline marker, but all business operations still retain full administrator-only history in `操作记录`. Existing reservations have no historical operator and are shown as historical/unrecorded in the editor and details until their next actual change. Unsaved form edits are not logged. The actor comes from the authenticated database session, never client-submitted metadata. Direct database/service operations without a user session are explicitly labeled `系统/数据库操作`.

Administrators have an `操作记录` menu with operator, date (Japan time, inclusive), region, business type, action and exact record-ID filters, paginated at 50 entries. Expand a log to inspect before/after values, including deleted records. Both the API and database row-level security restrict history to administrators; ordinary users cannot write, edit or delete the log table. History has no foreign-key cascade to business records or user accounts, so it survives deletion. Company seal changes store fingerprints rather than image data. Auth credentials, passwords, access tokens and login/reset-password events are not collected; account administration is separate from these business-record logs. The log contains business/customer data and should be covered by database backup, retention and access policies. No automatic log purge is configured.

Run the focused application tests with `node --test tests/business-audit.test.mjs`. The SQL regression script `supabase/tests/business_audit.sql` uses temporary fixture accounts and records in a transaction ending in `ROLLBACK`; run it only in a development database with the migrations applied. It checks authenticated attribution, no-op upserts, forged metadata, administrator-only history, image redaction, invoice reuse, audit-failure rollback and retention after cascaded record/account deletion.

Vehicle statistics (`車両統計`), balance (`收支平衡`) and login account management are visible only to accounts with the `admin` role. A `役员` position alone does not grant access. The dashboard API skips vehicle-monthly-finance and balance-expense queries for non-admin accounts and rejects mutations of these collections with HTTP 403. Other authorized order/wage/vehicle-management features remain unchanged. This application-level restriction does not change the existing database RLS policies or remove ordinary users' order finance access.

The local environment and production deployment may connect to different Supabase projects. Merging source code does not copy production accounts, credentials, or operational records. Do not replace local environment settings with production secrets or deploy the merged code before validating database migrations.

Vehicle schedule conflicts are checked when creating **and** when saving an edited reservation (the order being edited is excluded). A conflict is any non-cancelled order in the same region that shares an active date (rest days excluded) with the same vehicle **or the same driver**. Per-day vehicle/driver assignments from order financial statistics override the order defaults for that day; blank drivers are ignored. Reservations without a 配車時間 (missing or invalid time) never conflict, on either side. For two single-day orders, departures less than 2 hours apart count as a conflict; multi-day orders with a time conflict on any shared active date. The warning lists each conflicting order with whether the vehicle and/or driver is duplicated, and lets you cancel or save anyway.

## Live data sync

After login, the dashboard re-reads business data from the server every 10 seconds while the tab is visible, and immediately when the window regains focus, so changes made by other users appear without a manual refresh. A background sync never overwrites local edits: it is skipped while any of your own saves are pending, and results from a fetch that started before a local edit are discarded. Failed sync attempts are retried silently on the next interval. Open forms keep their in-progress values; when two users edit the same record, the last save wins.

## Calendar vehicle rows and vehicle identity

The calendar shows one row per registered vehicle. Each row header displays that vehicle's own **車両番号** in large text with the vehicle name in small text below (missing plates show **未登记番号**).

Reservations reference their vehicle by **車両番号** (`orders.vehicle_plate`, plus `vehiclePlate` in per-day finance entries), so several vehicles may share the same name. Vehicle names may repeat freely; **車両番号 must be unique within a region** and adding, batch-adding or editing a vehicle to an existing plate is rejected with a warning. When a name is shared by several vehicles, the reservation form asks for the specific 車両番号 before saving. Conflict checks compare plates when both reservations have one. Renaming a vehicle or changing its plate updates the reservations linked to it.

Migration `20261030000000_order_vehicle_plate.sql` adds the column and backfills plates for reservations whose car name matched exactly one vehicle in its region. Older reservations on a shared name keep an empty plate; they appear in every row with that name until you open them and pick the 車両番号.

### Calendar vehicle order

Vehicles that are out of service (status 停运中 or an expired 車検/自賠責) are always listed last. Otherwise the default order is Alphard 四代 → Alphard 三代 → Alphard → Hiace → Alphard 二代 → Tesla → other → 外注.

Drag the ⠿ handle on the left of a calendar row onto another row to reorder. The order is saved in `vehicles.calendar_order` (migration `20261031000000_vehicle_calendar_order.sql`) and shared by all users. Vehicles that have never been dragged follow the reordered ones in the default order. **恢复默认顺序** clears the manual order for the current region.
