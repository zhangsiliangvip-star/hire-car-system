# Hire Car System

Next.js dashboard for hire-car operations across the Tokyo, Osaka, and Hokkaido regions. Business records are stored in Supabase PostgreSQL. Supabase Auth handles email/password sign-in, and database row-level security isolates ordinary users by region while administrators can access all regions.

## Login management

Login management opens account creation/editing in a native modal dialog with focus containment, a scrollable card layout and a sticky close header. Escape/close clears password drafts; closing is blocked during account writes. Profile saving and independent password resets retain their existing behavior, with errors and password-reset feedback shown inside the modal.

## Vehicle expiry dates

Vehicle inspection and compulsory-liability expiry editors accept Japanese era/year/month/day fields and preview the converted Gregorian date. Enter `1` for the first year of an era; invalid dates, dates outside the chosen era and incomplete entries block saving. Existing Gregorian dates are converted back when editing; lists, order details, storage, imports and expiry reminders continue to use Gregorian `YYYY-MM-DD`. Clearing the date remains supported. No database migration is required.

## Supabase setup

1. ### Independent driver and staff sessions

The driver portal (`/driver`) and staff workspace (`/login`) keep separate Supabase sessions in the same browser or device. Signing in, refreshing authentication, or signing out of one portal does not replace or end the other portal's session. Driver pages and `/api/driver/*` use the driver cookie; staff pages and staff APIs retain the original staff cookie and permission checks. Each scope has its own cached browser client, with the SDK's shared singleton disabled.

After upgrading from the shared-session version, drivers must sign in once again at `/driver/login`; existing staff sessions remain compatible. No account or database migration is needed. Email callbacks choose the session scope from their same-origin destination.

The driver client explicitly persists its session and automatically refreshes tokens while the browser is active. The SDK's persistent cookies (up to 400 days) allow session restoration when reopening the browser; this is not a guaranteed login duration. Server-side session expiry or revocation, signing out, and browser storage cleanup can still require another login. A short-lived access token expiring does not itself require signing in again when its refresh token remains valid.

Vehicle schedule conflicts are checked when creating **and** when saving an edited reservation (the order being edited is excluded). A conflict is any non-cancelled order in the same region that shares an active date (rest days excluded) with the same vehicle **or the same driver**. Per-day vehicle/driver assignments from order financial statistics override the order defaults for that day; blank drivers are ignored. Reservations without a 配車時間 (missing or invalid time) never conflict, on either side. For two single-day orders, departures less than 2 hours apart count as a conflict; multi-day orders with a time conflict on any shared active date. The warning lists each conflicting order with whether the vehicle and/or driver is duplicated, and lets you cancel or save anyway.

## Live data sync

After login, the dashboard re-reads business data from the server every 10 seconds while the tab is visible, and immediately when the window regains focus, so changes made by other users appear without a manual refresh. A background sync never overwrites local edits: it is skipped while any of your own saves are pending, and results from a fetch that started before a local edit are discarded. Failed sync attempts are retried silently on the next interval. Open forms keep their in-progress values; when two users edit the same record, the last save wins.

## Calendar vehicle rows and vehicle identity

The calendar shows one row per registered vehicle. Each row header displays that vehicle's own **車両番号** in large text with the vehicle name in small text below (missing plates show **未登记番号**).

Reservations reference their vehicle by **車両番号** (`orders.vehicle_plate`, plus `vehiclePlate` in per-day finance entries), so several vehicles may share the same name. Vehicle names may repeat freely; **車両番号 must be unique within a region** and adding, batch-adding or editing a vehicle to an existing plate is rejected with a warning. When a name is shared by several vehicles, the reservation form asks for the specific 車両番号 before saving. Conflict checks compare plates when both reservations have one. Renaming a vehicle or changing its plate updates the reservations linked to it.

Migration `20261030000000_order_vehicle_plate.sql` adds the column and backfills plates for reservations whose car name matched exactly one vehicle in its region. Older reservations on a shared name keep an empty plate; they appear in every row with that name until you open them and pick the 車両番号.

## Staying signed in

Supabase sessions persist in cookies and are refreshed by `proxy.ts`, so staff and drivers stay signed in until they log out. A signed-in user who opens `/login` or `/driver/login` is redirected to the page for their role (staff to the dashboard or a safe `next` path, drivers to `/driver`); if the role check fails, the login form is shown. Logout uses `signOut({ scope: "local" })` so it only ends the session on the current device. WeChat's in-app browser may clear cookies, so drivers should open the app in Safari/Chrome or add it to the home screen.
